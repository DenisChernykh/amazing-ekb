# ARCHITECTURE_GUIDELINES.md

---

## 1. Разделение по слоям (Layered Architecture)

- **UI/Presentation (frontend, server actions):**
  Только сбор данных, структурная/типовая валидация через zod, преобразование в DTO, возврат ошибок для пользователя.
- **Use-case (бизнес-логика):**
  Принимает только валидированные DTO, реализует только бизнес-правила, не содержит валидации input/структуры, не работает с FormData/raw.
- **Adapter/Repository (инфраструктурный слой):**
  Отвечает за работу с БД, внешними API, сториджем. Явный mapping между инфраструктурой и бизнес-типами. Обработка и маппинг ошибок.
- **Инфраструктура (ORM/БД, сторонние сервисы):**
  Не трогается напрямую, только через adapter.

---

## 2. Типы данных

- **Все входные типы DTO выводятся через zod-схемы** (`z.infer<typeof schema>`).
- **ApiResponse** — универсальный generic для server actions, покрывает успех, ошибки валидации, бизнес-ошибки и сообщения для UI.
- **Result** — тип для use-case, содержит только `success/data` или `success: false; error`.

---

## 3. Валидация

- **Структурная и типовая валидация** — только в presentation слое (server action, API-эндпоинты).
- **Валидация через zod (или аналог), никаких классов-валидаторов, никакого ручного кода.**
- **Ошибки валидации возвращаются в поле `errors` в ApiResponse как массив ZodIssue[].**
- **В use-case допускается только бизнес-валидация, которую нельзя выразить через zod (например, "категория должна быть активной").**

---

## 4. Обработка ошибок

- **Бизнес-слой возвращает только error code, не кидает исключения наружу.**
- **Server action маппит ошибки валидации и бизнес-логики в понятные сообщения для UI.**
- **В ApiResponse обязательно есть поле message (для тостов, алертов, общего UX).**

---

## 5. DI и зависимости

- **Все внешние зависимости (репозитории, резолверы, логгеры) передаются в use-case через конструктор (Dependency Injection).**
- **Value-object и чистые утилиты можно создавать через new внутри класса.**
- **Нет прямой зависимости бизнес-логики от ORM, API и др. инфраструктуры.**

---

## 6. Mapping

- **Любой переход между слоями — только явный mapping (никаких `as Type`, никаких any).**
- **Маппинг из ORM/Prisma/Supabase — в отдельной функции внутри adapter.**
- **Маппинг ошибок из инфраструктуры в error-коды бизнес-слоя — всегда централизован.**

---

## 7. Типизация

- **Никаких any ни на одном слое (допустим только временно для внешних библиотек, но всегда заменять на строгие типы).**
- **Все типы экспортируются из одного места, чтобы не было дублирования.**

---

## 8. Чистота кода

- **Нет дублирования бизнес-логики между слоями.**
- **Нет ручного парсинга FormData внутри use-case.**
- **Server action — только bridge между формой и use-case (валидация, вызов, возврат ответа).**
- **UI всегда получает полный и предсказуемый ответ для UX.**

---

## 9. Масштабируемость и тестируемость

- **Каждый слой легко мокается и покрывается unit-тестами.**
- **Изменения бизнес-правил затрагивают только use-case.**
- **Инфраструктура подменяется через DI, маппинг — в одном месте.**

---

## 10. Общие стандарты

- **ApiResponse<T, E> — стандартный тип для server action.**
- **Result<T, E> — стандартный тип для use-case.**
- **Валидация через zod.**
- **DI через конструктор.**
- **Все архитектурные решения фиксируются в этом файле и пересматриваются на командных ревью.**
